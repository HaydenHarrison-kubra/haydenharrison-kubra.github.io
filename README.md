# KUBRA Style Guide 2.0 — interactive site

A searchable, static website built from the Confluence page **[Style Guide 2.0](https://kubra.jira.com/wiki/spaces/CD/pages/2016313568/Style+Guide+2.0)** (space: Design, cloud: kubra.jira.com) and its 31 sub-pages, covering content structure, foundations (voice/tone/accessibility), system messages, controls and inputs, forms and flows, compliance and legal, and reference and governance.

## Features

- **KUBRA branding** — KUBRA blue/navy palette with green and yellow accents, Montserrat headings (KUBRA's brand typeface) and Inter body text.
- **Search** — live, full-text search across every page and the glossary, with highlighted snippet previews. Press `/` or `⌘K` / `Ctrl K` to jump to it, and `Enter` to open the top result. Opening a result scrolls to the first match on the page and highlights every match, with a bar to step through them.
- **Deep links** — every heading has a copy-link button; links like `#buttons-and-ctas/avoid-the-word-click` open the page scrolled to that section.
- **Standard Copy** — approved, ready-to-paste messages (standard error message, SMS compliance language) with one-click copy and highlighted placeholders. Edit them in `content/standard-copy.json`.
- **Glossary** — an A–Z, filterable list of approved product names, abbreviations, preferred terms, and internal terms to avoid, each linked back to its source page.
- **Automatic changelog and versions** — every publish that changes guide content or plugin rules becomes a new version (2.0.1, 2.0.2, …), listed on the Changelog page, and every page shows when it was last updated. Nobody writes changelog entries by hand (see [Changelog and versions](#changelog-and-versions)).
- **Section navigation** — collapsible sidebar grouped the same way as the Confluence space, section landing pages, breadcrumbs, and previous/next links on every page.
- **On this page** — a sticky table of contents on wide screens that tracks your scroll position.
- **Topic filters** — Accessibility / Payments / Errors & Messaging chips dim non-matching pages in the sidebar and narrow search results.
- **Copy-able examples** — every "do" and "don't" example line gets a copy button on hover.
- **Light / dark mode** — toggle in the header, remembered via `localStorage`, and respects the OS preference by default.
- Fonts load from Google Fonts; otherwise no build step — plain HTML/CSS/JS plus Markdown, so it runs the same locally and on GitHub Pages.

## Files

- `content/pages/<slug>.md` — one Markdown file per guideline page (31).
- `content/sections/<slug>.md` — the intro shown on each section's landing page (7).
- `content/overview.md` — the intro shown on the home page.
- `content/sections.json` — sidebar sections, page order, and topic filters.
- `content/glossary.json` and `content/standard-copy.json` — the Glossary and Standard Copy.
- `index.html` — the page shell.
- `styles.css` — all styling, including light/dark theme tokens.
- `app.js` — loads and renders the Markdown, plus routing (`#page` or `#page/section`), search, filters, glossary, changelog, copy buttons, and theme toggle.
- `vendor/marked.umd.js` — the Markdown renderer ([marked](https://github.com/markedjs/marked) v18.1.0, MIT), kept in the repo so the site doesn't depend on a CDN.
- `.nojekyll` — tells GitHub Pages to serve the `.md` files as-is instead of converting them.
- `figma-plugin/` — the **KUBRA Copy Audit** Figma plugin, which checks Figma text against this guide. See [figma-plugin/README.md](figma-plugin/README.md).
- `rules.json` — the plugin's rules, generated by `node figma-plugin/build.mjs` from the glossary, standard copy, and the plugin's rule files. Rebuilt automatically on every publish.
- `changelog.json` — generated by `scripts/changelog.mjs` from git history on every publish. Don't edit it by hand; settings and pre-automation notes are in `changelog.config.json`.
- `.github/workflows/publish.yml` — builds and publishes the site on every push to `main`.

## Editing page content

Each page file starts with a short header, then standard Markdown:

```md
---
title: "Buttons and CTAs"
blurb: "Action-oriented, accessible button copy."
topics: ["Accessibility", "Payments"]
---

Buttons initiate actions. ...

## Use clear, action-oriented language
```

- `title` and `blurb` appear in the sidebar, page header, section page, and search. `topics` (optional) power the topic filters: `"Accessibility"`, `"Payments"`, `"Errors & Messaging"`.
- Use `##` for page sections (they appear in "On this page") and `###` below that.
- Do and don't examples use fenced blocks. Blocks next to each other (separated only by blank lines) become one side-by-side table:

  ```md
  ::: do
  - *Pay bill*
  - *Save changes*
  :::

  ::: dont
  - *Submit*
  :::
  ```

  Add a custom header after the type, e.g. `::: do Use as product name` or `::: dont Avoid`. To place two separate tables back to back, put `<!-- -->` between them.
- Highlighted panels: `::: callout` (blue) and `::: note` (yellow), closed with `:::`.
- Tables use standard Markdown pipe tables. Bare email addresses and URLs are not auto-linked; write links as `[text](https://…)`.

**Adding a page:** create `content/pages/<slug>.md`, then add the slug to that section's `children` list in `content/sections.json` (the order there is the sidebar order).

## Previewing locally

The site loads its content with `fetch`, so opening `index.html` directly from disk won't work. From the repo folder, run `node scripts/changelog.mjs` (to refresh the changelog and page dates; unpublished commits show as "Unreleased"), then `python3 -m http.server` and open `http://localhost:8000`.

## Publishing

The site is live at **https://haydenharrison-kubra.github.io/**. Every push to `main` runs the **Publish site** GitHub Action (`.github/workflows/publish.yml`), which:

1. rebuilds and tests the Figma plugin rules,
2. tags a new version if guide content or plugin rules changed,
3. regenerates the changelog and page dates, and
4. deploys to GitHub Pages.

So publishing is just committing and pushing:

```
git add -A
git commit -m "Clear, user-facing summary of the change"
git push origin main
```

The update appears a minute or two later. Check progress in the repo's **Actions** tab. GitHub Pages must be set to deploy from GitHub Actions (Settings → Pages → Source: **GitHub Actions**).

## Changelog and versions

The Changelog page and every page's "Updated" date are generated from git history. There's nothing to update by hand.

- **Versions:** each push that changes guide content (`content/`) or plugin rules (`figma-plugin/rules/`, `figma-plugin/config/`) gets the next version, like 2.0.5, as a git tag. Pushes that only change site code or styling don't create a version. For a bigger release, change `version` in `changelog.config.json` to `"2.1"` (or `"3.0"`), and numbering continues at 2.1.0.
- **What each entry says:** the summary line of each commit in that push, so write commit messages for readers, like “Add guidance on loading-state button labels.” Generic messages from GitHub's web editor, like “Update forms.md,” become “Updated Forms.”
- **Leaving something out:** put `[skip changelog]` in a commit message, for example for typo fixes or file moves that don't change meaning.
- **Page dates:** each page shows the date and version of the last change to its file.

## Keeping it in sync with Confluence

The site started as a snapshot of the Confluence content, and some guidance has since been added here first. When the style guide changes in Confluence:

1. Re-pull the updated page(s) and update the matching file(s) in `content/` (asking Claude to do this is the fastest way).
2. If product names, abbreviations, or preferred terms changed, update `content/glossary.json`.
3. Commit with a message that says what changed, and push. The changelog, page dates, and plugin rules update on their own.
